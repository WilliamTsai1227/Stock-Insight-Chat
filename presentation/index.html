01 · SSE 串流

問題：使用者關頁面，整個回合就沒了

LLM 回應需要 10–30 秒。若直接在 SSE generator 內跑 LLM——

觸發

使用者關頁面 / 斷線，SSE 連線中止，協程收到 asyncio.CancelledError。

後果

整個 LangGraph 回合被 cancel，多輪檢索與分析全部作廢。

代價

DB 沒有任何 assistant 紀錄，但 OpenAI 的 token 費用照樣發生。

本質：把 LLM 綁在 HTTP 連線生命週期上，是一個隱性的耦合。

01 · SSE 串流

解法：Queue 解耦，生產者在背景跑完

  • 每個請求建一個 asyncio.Queue
  • LLM 回合用 create_task 當生產者在背景執行
  • SSE generator 當消費者，只 queue.get() → yield
  • 斷線只 cancel 消費者；生產者跑完整個 LangGraph、寫入 PostgreSQL
  • put(None) 哨兵置於 finally，保證收尾送達
async def background_agent_runner():
    try:
        async for ev in agent_app.astream_events(...):
            await q.put(_sse(...))   # 生產者
        await q.put(_sse("done", {...}))
        await _insert_assistant_message(...) # 落 DB
    finally:
        await q.put(None)         # 收尾哨兵

asyncio.create_task(background_agent_runner())

async def event_generator():        # 消費者
    while True:
        msg = await q.get()
        if msg is None: break
        yield msg
01 · SSE 串流

本質：業務邏輯與連線狀態解耦

把「對話要不要繼續產生」（業務邏輯）與
「使用者有沒有在看」（連線狀態）兩件事切開。

  • 斷線後重整，能從 DB 拿回已定稿的回答，不靠「運氣接上串流」
  • 可延伸為獨立 job queue / 多 worker——SSE 只是最佳努力的即時進度
  • 要補的護欄：每使用者併發上限、逾時、取消語意（已列在設計文件）
02 · LangGraph Agent

成本結構驅動的角色拆分

Routergpt-5-mini（便宜）

  • 只做意圖辨識與工具決策
  • 支援 ReAct 多輪：搜尋 → 看結果 → 再精確搜尋
  • system prompt 明文禁止產出總結，避免便宜模型浪費 token 寫長文

Analystgpt-5（貴）

  • 拿到完整檢索資料後一次性產出投資分析報告

  • 讓貴的模型只在最關鍵那一步出手

同一份 LangGraph 狀態圖，依角色綁不同模型——這是可量化的成本設計，不是為了用兩個模型。

03 · Hybrid RAG

Chunking：不同資料用不同策略

新聞 · 語意段落切分

  • RecursiveCharacterTextSplitter　800 / overlap 150
  • 優先在段落 / 句號斷開
  • 短文不切（full）；長文才切（partial）
  • 每段前綴 [標題] → 脫離上下文仍可被正確檢索

AI 分析 · 按欄位語意角色

  • 不做二次字元切割，按角色拆最多 3 個向量
  • summary　產業近況
  • key_news　具體事件
  • stock_insight　個股推薦
  • 不同查詢意圖 → 命中不同角色向量
03 · Hybrid RAG

Hybrid 檢索：dense + BM25，用 RRF 融合

為什麼 Hybrid

  • dense（1536 維 cosine）抓語意
  • BM25 sparse 抓精確詞（如股票代碼「2330」）
  • RRF 融合排名，非分數相加——兩者分數尺度不同

分組去重

search_groups(group_by="mongo_id", group_size=2)：同一篇長文的多個 chunk 不會洗版 top-k。

Metadata 過濾

  • 時間區間　Datetime index
  • 股票代碼 / 名稱　Keyword
  • 新聞類型　Keyword
  • 情緒標籤　Keyword
  • 產業　Keyword

相似度門檻過濾低相關；必要時由 mongo_id 回 MongoDB 提領全文。

04 · Context 工程

問題：Router 上下文爆炸（兩層根因）

① 歷史層

Router 每次呼叫都收到完整 DB 對話歷史；歷史一長，prompt 就肥。

② 同輪累積層

同一問題內 Router 多輪重試，每輪 ToolMessage 疊加進 state；第 3 次進 Router 已含前兩批全部工具結果 → token 暴增。

Router 第 3 次： Human | AI(calls A) | Tool_A1 Tool_A2 | AI(calls B) | Tool_B1
                                    ↑ 前兩批工具結果全都還在 prompt 裡
04 · Context 工程

雙軌保護 + 用 token log 量化驗證

核心洞察

Router 只需知道「叫哪個工具、有沒有找到」；只有 Analyst 需要完整內容。

Tool（截斷 500 字） → messages     # Router 決策
原始完整資料        → retrieved_data # Analyst 分析
  • Router 只看最近 2 輪歷史（ROUTER_HISTORY_TURNS）
  • 同輪 ToolMessage 只留最新一批
  • DB 舊 Analyst 報告截斷 800 字；檢索 top-k 15→5

如何驗證？逐輪 token log

每輪 Router / Analyst 的 prompt、completion tokens 都寫入 token_usage_logs。

  • Router 首輪 prompt tokens　高 → 明顯下降
  • 同輪重試累積　爆炸 → 下降
  • Analyst 品質　不變（雙軌保護）

優化前後拿「同類型對話」直接比對——量化驗證，不憑感覺。

04 · 認證安全

JWT RT Rotation + 重放攻擊偵測

Token存放防護
AT
15 分鐘		JS 記憶體變數
不落 localStorage		防 XSS；
stateless 不查 DB
RT
7 天		HttpOnly Cookie
SameSite=Lax		JS 不可讀防 XSS；
SameSite 防 CSRF
DELETE FROM refresh_tokens
WHERE token = $1 AND expires_at > NOW()
RETURNING user_id;   -- 原子消費

DELETE = 0 列，但簽名仍有效

→ 判定 Token Reuse Attack → 立即撤銷該用戶所有 session。無法區分駭客與本人誰先用，全撤最安全。

04 · 認證安全

前端並發鎖：沒有它會被自己誤判成攻擊

沒有並發鎖的競態

  • 兩個並發 401 → 同時觸發兩次 refresh
  • 第一次：rotation 成功，舊 RT 被刪
  • 第二次：持已消費的舊 RT → 被判 Reuse Attack
  • 使用者被自己踢下線、全裝置登出

三機制（auth.js）

  • A　AT 到期前 60s 背景靜默 refresh
  • B　請求前檢查效期 + 401 自動重試（兜底）
  • C　並發鎖：共用同一個 refresh Promise，併發請求都等同一結果
04 · 配額計量

兩道防線，與一個刻意的取捨

① Pre-flight（入口攔截）

進 LangGraph 前檢查 used_tokens ≥ monthly_limit → 直接 429，不開串流。

② 原子遞增 + 最終一致

每輪 LLM 結束 UPDATE … used_tokens += delta，與寫 token_usage_logs 同一 transaction。計數器與流水分表。

刻意允許單輪略超（最終一致）

不在超限當下中斷回合（避免「還有額度卻被砍半篇回應」），由下一輪 pre-flight 攔截。

若改以成本嚴格為優先 → 條件式 UPDATE … WHERE used_tokens + delta ≤ limit（原子強制不超扣），代價是可能中斷正在串流的回合。我選前者，因為使用者體驗優先。

總結

每個設計背後，都是一個能說清楚的取捨

斷線仍持久化

vs 省成本中止背景任務。
我選持久化：對話結果是「真相來源」。

允許單輪略超配額

vs 嚴格不超扣。
我選最終一致：使用者體驗優先。

截斷給 Router

vs 完整給 Analyst。
雙軌兼顧成本 / 延遲 / 品質。

共同點：有意識地選，並且用 token log / 競態分析支撐——不是憑感覺。
